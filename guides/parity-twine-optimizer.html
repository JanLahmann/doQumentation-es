Parity Twine Optimizer de ParityQC

Consulta la referencia de la API

nota

Información general​

El Parity Twine Optimizer permite a los usuarios resolver problemas de optimización con computadoras cuánticas utilizando el método Parity Twine. Este enfoque, basado en la Parity Architecture, utiliza el compilador de ParityQC para minimizar el número de puertas y la profundidad del circuito necesarios para ejecutar un algoritmo cuántico, teniendo en cuenta la conectividad del dispositivo.

Esta reducción de recursos permite resolver problemas de optimización relevantes para la industria en tamaños que resultan inviables con los métodos de transpilación estándar, que hacen un uso intensivo de SWAP. El Parity Twine Optimizer automatiza los pasos de transpilación y puede utilizarse con una mínima intervención del usuario.

El enfoque Parity Twine supera a todos los demás métodos de compilación en términos de reducción del número de puertas y de la profundidad de los circuitos para algoritmos cuánticos como el algoritmo de optimización aproximada cuántica (QAOA) y la transformada cuántica de Fourier (QFT). Al abstraer la información cuántica de los qubits físicos, las interacciones no locales se implementan sin puertas SWAP. En cambio, las cadenas Parity Twine (secuencias de puertas CNOT) distribuyen sistemáticamente la información de paridad lógica entre los qubits.

El optimizador utiliza el QAOA para minimizar la energía de una función de costo dada. El QAOA es un algoritmo variacional híbrido cuántico-clásico diseñado para resolver problemas de optimización combinatoria aproximando el estado fundamental de un hamiltoniano de costo (HCH_CHC​). Un término de mezcla (HBH_BHB​) impulsa las transiciones entre estados para explorar el espacio de soluciones. Una secuencia alternante de estos términos, controlada por los parámetros γ\gammaγ y β\betaβ, define la unitaria U(γ,β)=Πi=1pe−iβiHBe−iγiHCU(\gamma, \beta) = \Pi_{i=1}^p e^{-i \beta_i H_B} e^{-i \gamma_i H_C}U(γ,β)=Πi=1p​e−iβi​HB​e−iγi​HC​, que actúa sobre el estado inicial.

La codificación de la unitaria del problema, exp(−iβHC)-i \beta H_C)−iβHC​)), requiere codificar todos los operadores lógicos de rotación de nnn cuerpos (exp(−iβJi,j,...nZiZj...Zn-i \beta J_{i,j,...n}Z_iZ_j...Z_n−iβJi,j,...n​Zi​Zj​...Zn​)). Esto puede lograrse utilizando generadores de nnn cuerpos (Parity Twine Networks), que reducen la profundidad del circuito de QAOA y el número de puertas de dos qubits.

Descripción​

La entrada del Parity Twine Optimizer consiste en un problema de optimización, el nombre del hardware de IBM Quantum elegido y argumentos opcionales adicionales para personalizar los ajustes de transpilación y de ejecución en el hardware. La función optimizadora dirige la definición del problema al Parity Twine Compiler. La Figura 1 muestra un resumen del flujo de trabajo de la función.

El problema de optimización de entrada se preprocesa para obtener un hamiltoniano (normalizado). A continuación, el compilador de ParityQC construye un circuito ansatz parametrizado de Parity Twine, que se transpila a un ansatz lógico que coincide con el conjunto nativo de puertas del hardware elegido.

Los parámetros del circuito de QAOA se optimizan de forma clásica utilizando el enfoque "efficient depth one" y se asignan al circuito transpilado. Como se utiliza una sola ronda de QAOA, los parámetros óptimos γ\gammaγ y β\betaβ se obtienen mediante una búsqueda en cuadrícula en una CPU, sin necesidad de una costosa optimización iterativa sobre muchas llamadas al circuito. Esto minimiza en gran medida el tiempo de ejecución en la QPU requerido por el optimizador. El tiempo de ejecución por circuito está determinado principalmente por la sobrecarga constante de ejecutar un trabajo en la QPU. Una vez configurados los parámetros del circuito, el trabajo se envía a la QPU de IBM® especificada.

Los resultados sin procesar se posprocesan a continuación. Este paso utiliza una búsqueda voraz local que recorre aleatoriamente la cadena de solución e invierte los valores de los bits si esto reduce el valor de la función de costo.

Aviso

El rendimiento puede depender tanto de la instancia del problema como de los pasos de procesamiento posteriores. En algunos casos, las muestras clásicas y las muestras generadas cuánticamente pueden alcanzar una calidad de solución final similar después de un posprocesamiento equivalente. Por lo tanto, la evaluación debe considerar el flujo de trabajo de optimización completo.

Tamaños de función​

Cada job se ejecuta con un único tamaño: S, M o L. Si el tamaño es demasiado pequeño, el job se rechaza. Si es mayor de lo necesario, el job se ejecuta en un perfil de cómputo más grande de lo que requiere el trabajo. Consulta Function sizes para saber cómo funcionan los tamaños en general.

El tamaño depende de dos propiedades de tu modelo: cuántas variables tiene y con qué densidad interactúan, es decir, la fracción de todos los pares de variables que aparecen juntos en un término de la función objetivo o de una restricción.

TamañoMenor tamaño para variables y densidad de interacciónPerfil de cómputovCPURAM
SComo máximo 50 variables y densidad como máximo 0.18x32832 GB
MComo máximo 100 variables y densidad como máximo 0.2516x12816128 GB
LPor encima del límite de M en cualquiera de los dos16x12816128 GB

Un modelo debe cumplir ambos límites de un tamaño, por lo que un modelo pequeño pero fuertemente acoplado puede ser L: diez variables acopladas todas entre sí dan una densidad de 1.0. Estos son los mismos límites para todas las funciones de optimización, de modo que un tamaño significa la misma dificultad de modelo sea cual sea la función que llames.

Dos cosas aumentan la densidad más de lo que parece:

  • Un término sobre más de dos variables acopla todos los pares entre ellas. Un término en cuatro variables aporta los seis pares.

  • Una restricción cuenta como la penalización que la sustituye en el hardware. Elevar la restricción al cuadrado acopla todos los pares de variables que contiene, así que una restricción one-hot sobre cuatro variables también aporta los seis pares.

El valor predeterminado es M, que se usa cuando un job no solicita un tamaño.

También puedes leer la correspondencia desde la propia función con function.sizes_map, y el tamaño predeterminado con function.default_size. Para el Parity Twine Optimizer, cada variable que aparece en problem cuenta una vez, y cada término cuadrático como "(0, 1)" aporta un par. El modelo del ejemplo tiene cinco variables y uno de los diez pares posibles, una densidad de 0.1, por lo que necesita S. Los modelos totalmente conectados, como el modelo de Sherrington-Kirkpatrick o la forma QUBO del problema de market split, tienen una densidad de 1.0 y siempre necesitan L.

Calcula el tamaño antes de enviar​

Ejecuta la siguiente calculadora sobre tu propio modelo. Lee el modelo y nada más: no se envía ningún job ni se reserva nada, así que puedes llamarla tantas veces como quieras mientras reduces un modelo a un tamaño menor.

# Calculate the function size a model needs, before submitting it.
# Call ``calculate_function_size(problem)``: it returns "S", "M" or "L" and submits
# nothing. The size comes from the number of variables and how densely they interact.

import ast

from collections.abc import Iterator
from itertools import combinations
from typing import Any, Literal

from qiskit_addon_opt_mapper.problems import OptimizationProblem

Size = Literal["S", "M", "L"]
VariableType = Literal["spin", "binary"]
_ORDER = {"S": 0, "M": 1, "L": 2}

# Limits are provided by IBM
_SMALL_NUMVARS, _SMALL_DENSITY = 50, 0.1
_MEDIUM_NUMVARS, _MEDIUM_DENSITY = 100, 0.25

def calculate_function_size(
    problem: dict[str, float] | OptimizationProblem, **kwargs: Any
) -> Size:
    """Return the size ("S", "M" or "L") needed to run ``problem``."""
    metrics = _measure(problem, **kwargs)
    if _is_small(metrics):
        return "S"
    if _is_medium(metrics):
        return "M"
    return "L"

def to_optimization_problem(
    problem: dict[str, float] | OptimizationProblem,
    problem_type: str = "",
    variable_type: VariableType = "binary",
) -> OptimizationProblem:
    """Convert the Parity Twine Optimizer ``problem`` input into an
    ``OptimizationProblem``.

    Args:
        problem: A dictionary {term: coefficient} where each term is a string
            version of a tuple of variable ids, for example
            {"()": 3, "(0,)": 1, "(0, 1)": 2}. An ``OptimizationProblem`` is
            returned unchanged.
        problem_type: The ``problem_type`` passed to the function, for
            example "mis".
        variable_type: Type of all variables, either "spin" or "binary".

    Returns:
        The parsed problem, as a minimization without constraints.
    """
    if isinstance(problem, OptimizationProblem):
        return problem

    if variable_type not in ("spin", "binary"):
        raise ValueError(
            f"Invalid variable type {variable_type!r}, expected 'spin' or 'binary'."
        )

    constant: float = 0
    linear_terms: dict[str, float] = {}
    quadratic_terms: dict[tuple[str, str], float] = {}
    variables: set[str] = set()

    for raw_term, coefficient in problem.items():
        try:
            parsed = ast.literal_eval(raw_term)
        except (ValueError, SyntaxError) as exc:
            raise ValueError(
                f"Invalid problem term {raw_term!r}: expected a tuple literal like '(0, 1)'."
            ) from exc
        if not isinstance(parsed, tuple):
            raise ValueError(
                f"Invalid problem term {raw_term!r}: expected a tuple literal like '(0, 1)'."
            )
        term = tuple(map(str, parsed))
        if len(term) == 0:
            constant = coefficient
        elif len(term) == 1:
            linear_terms[term[0]] = coefficient
        elif len(term) == 2:
            quadratic_terms[term] = coefficient
        else:
            raise ValueError(
                "Invalid problem term, only quadratic problems are "
                f"supported, higher-order term: {term}"
            )
        variables.update(term)

    model = OptimizationProblem()
    model.name = problem_type
    for variable in sorted(variables):
        if variable_type == "spin":
            model.spin_var(variable)
        else:
            model.binary_var(variable)

    model.minimize(
        constant=constant, linear=linear_terms, quadratic=quadratic_terms
    )
    return model

def _measure(
    problem: dict[str, float] | OptimizationProblem, **kwargs: Any
) -> dict[str, float]:
    """Return the number of variables and the interaction density."""
    model = to_optimization_problem(
        problem,
        problem_type=kwargs.get("problem_type", ""),
        variable_type=kwargs.get("variable_type", "binary"),
    )
    num_vars = model.get_num_vars()

    pairs = set()
    for term in _interactions(model):
        pairs.update(frozenset(pair) for pair in combinations(set(term), 2))

    max_pairs = num_vars * (num_vars - 1) // 2
    return {
        "num_vars": num_vars,
        "density": len(pairs) / max_pairs if max_pairs else 0.0,
    }

def _interactions(problem: OptimizationProblem) -> Iterator[tuple[int, ...]]:
    """Yield the variables of every term that couples two or more of them.

    A constraint contributes every variable in it, because on hardware it becomes
    a penalty whose square couples them all.
    """
    objective = problem.objective
    yield from objective.quadratic.to_dict()
    for expression in objective.higher_order.values():
        yield from expression.to_dict()

    for constraint in problem.linear_constraints:
        yield _constraint_support(constraint)
    for constraint in problem.quadratic_constraints:
        yield _constraint_support(constraint)
    for constraint in problem.higher_order_constraints:
        yield _constraint_support(constraint)

def _constraint_support(constraint: Any) -> tuple[int, ...]:
    """Return every variable appearing in a constraint's left-hand side."""
    variables = set(constraint.linear.to_dict())
    if hasattr(constraint, "quadratic"):
        for term in constraint.quadratic.to_dict():
            variables.update(term)
    if hasattr(constraint, "higher_order"):
        for expression in constraint.higher_order.values():
            for term in expression.to_dict():
                variables.update(term)
    return tuple(variables)

def _is_small(metrics: dict[str, float]) -> bool:
    """Determine if the metrics fit T-size 'S'."""
    return (
        metrics["num_vars"] <= _SMALL_NUMVARS
        and metrics["density"] <= _SMALL_DENSITY
    )

def _is_medium(metrics: dict[str, float]) -> bool:
    """Determine if the metrics fit T-size 'M'."""
    return (
        metrics["num_vars"] <= _MEDIUM_NUMVARS
        and metrics["density"] <= _MEDIUM_DENSITY
    )

Si el tamaño es demasiado pequeño, el job falla con el error 4600 y el mensaje indica el tamaño que debes usar en su lugar. Si es mayor de lo necesario, el job se ejecuta con normalidad y registra un evento de aviso 4601. Consulta Function sizes para obtener más información.

Ejemplo​

El Parity Twine Optimizer puede aplicarse a un ejemplo sencillo de QUBO de la siguiente manera. El problema se define primero mediante un diccionario:

problem = {"()": 3.0, "(2,)": -1.0, "(3,)": 1.0, "(4,)": 1.0, "(0, 1)": 2.0}

Luego, el tipo de variable debe definirse como binary o spin:

variable_type = "spin"

Esto define la función objetivo 3−s2+s3+s4+2s0s13 - s_2 + s_3 + s_4 + 2 s_0s_13−s2​+s3​+s4​+2s0​s1​ donde si∈{−1,1}s_i \in \{-1, 1\}si​∈{−1,1}.

Elige un backend. Por ejemplo:

backend_name = "ibm_phoenix"
size = calculate_function_size(problem)
print(size)

Utiliza catalog.backends() para ver una lista de los backends disponibles de la cuenta/instancia del usuario.

Si no se especifica un backend, se selecciona automáticamente el backend menos ocupado (el que tiene el menor número de trabajos pendientes).

Una vez cargado el optimizador (consulta la sección anterior), puedes ejecutarlo sobre el problema utilizando las opciones predeterminadas. Este modelo necesita el tamaño de función S (consulta Function sizes):

function_job = function.run(
    problem=problem,
    variable_type=variable_type,
    backend_name=backend_name,
    function_size=size,
)
print(f"Job ID: {function_job.job_id}")

# Monitor the job status
